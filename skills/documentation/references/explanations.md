# Explanations Path

Use this path when the reader needs understanding, rationale, trade-offs, or a
mental model rather than task steps.

## Read First

- architecture notes
- design comments and ADRs if available
- code structure and dependency boundaries
- existing terminology in the repository

## Writing Rules

- explain why the system works this way
- surface trade-offs and alternatives
- connect concepts to real project structure
- avoid turning the document into a step-by-step guide

## Recommended Sections

- context
- key concepts
- decisions and trade-offs
- alternatives or non-goals
- implications for contributors or operators

## Validation Points

- claims about decisions are grounded in code or project artifacts
- terminology matches the codebase
- trade-offs are technical, not generic filler
- the document clarifies instead of duplicating reference material
